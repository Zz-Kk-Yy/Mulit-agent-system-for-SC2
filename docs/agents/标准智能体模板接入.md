# 标准智能体模板接入指南

本文说明如何基于 `create_new_agent.py` 快速接入新的 SC2 子智能体，并以 `sc2_counter.py` 为参考案例。该模板从 `sc2_agents.py` 中既有 6 阶段流水线配置提炼而来，将重复的 `SubagentConfig` 样板代码收敛为一次函数调用。

> **必读前置**：[SC2数据与智能体输入说明.md](./SC2数据与智能体输入说明.md) — SC2 里有哪些数据、六阶段各自**输入/输出 JSON**、主流水线如何注入 `thread_id`（§2.1）、不装游戏如何用 `fixtures/` 离线对接。  
> **编排脚本（副本）**：`run_sc2_deerflow_pipeline.py`  
> **样例数据**：`fixtures/*.sample.json`

---

## 0. 六阶段输入输出一览（对接用）

设计新智能体前，先确认自己要**读哪些上游 cache 键**（`input_sources`），不要重复拉原始态势。

| 阶段 | 缓存键 | 主要输入（`input_sources`） | 主要输出供谁用 |
|------|--------|----------------------------|----------------|
| sc2-sensing | `sensing` | **无**（读 `situation:current`） | 全流水线 |
| sc2-compute | `compute` | `sensing` | disposition、intent、扩展分析 |
| sc2-disposition | `disposition` | `sensing`, `compute` | intent、risk-id |
| sc2-intent | `intent` | `sensing`, `compute`, `disposition` | risk-id、risk-response |
| sc2-risk-id | `risk_id` | `sensing`, `compute`, `disposition`, `intent` | risk-response |
| sc2-risk-response | `risk_response` | `intent`, `risk_id` | 执行/仪表盘 |
| **示例 sc2-counter** | `counter` | `sensing`, `compute` | disposition、方案模块等 |

各阶段 **输出 JSON 字段表**、原始态势 `situation:current` 全字段、工具参数见 [SC2数据与智能体输入说明.md](./SC2数据与智能体输入说明.md)。

## 1. 背景与目标

### 1.1 流水线架构

SC2 态势分析采用**顺序流水线**：每个阶段读取上游产物、产出结构化 JSON、写入 Redis 缓存，供下游继续消费。

```
sc2-sensing → sc2-compute → sc2-disposition → sc2-intent → sc2-risk-id → sc2-risk-response
     │              │               │              │              │                │
     └──────────────┴───────────────┴──────────────┴──────────────┴────────────────┘
                              sc2_analysis_cache (按 thread_id 隔离)
```

### 1.2 模板 vs 手写配置

| 方式 | 适用场景 |
|------|----------|
| **`create_new_agent()`** | 新增标准分析型子智能体：职责清晰、依赖上游缓存、输出固定 JSON |
| **手写 `SubagentConfig`**（见 `sc2_agents.py`） | 流程复杂、需大量自定义 prompt 段落或特殊工具策略 |

新智能体**优先使用模板**；仅在模板无法表达的业务逻辑时，再参考 `sc2_agents.py` 手写完整配置。

---

## 2. 核心约定（所有智能体必须遵守）

以下规则由 `create_new_agent.py` 中的 `_COMMON_RULES` 自动注入到 `system_prompt`：

1. **读上游**：执行前先调用 `sc2_analysis_cache_get(thread_id)` 获取依赖的上游产物。
2. **写产物**：必须调用 `sc2_analysis_cache_set(thread_id, agent_name=..., payload=...)` 持久化 JSON。
3. **thread_id**：从编排层首条用户消息 `thread_id=...` 中逐字提取，不可臆造。
4. **输出格式**：最终只输出一次严格 JSON，禁止 markdown 代码块与思考过程。
5. **自主运行**：默认禁用 `task`、`ask_clarification`，避免子智能体进入对话澄清循环。

### agent_name 命名规则

- **注册名**（`SubagentConfig.name`）：带前缀，如 `"sc2-counter"`。
- **缓存键**（`sc2_analysis_cache_set` 的 `agent_name`）：取 `-` 后缀，如 `"counter"`。
- 模板会自动从 `agent_name.split('-')[-1]` 推导缓存键，请保持 `"sc2-<短名>"` 格式一致。

## 3. 模板 API 说明

文件：`create_new_agent.py`

```python
def create_new_agent(
    agent_name: str,           # 唯一标识，如 "sc2-counter"
    description: str,          # 简短描述，供编排层调度展示
    role: str,                 # 一句话职责
    input_sources: list[str],  # 依赖的上游 agent 缓存键，如 ["sensing", "compute"]
    output_json_schema: dict,  # 输出 JSON 结构（Python dict，会序列化进 prompt）
    extra_tools: list[str] = None,   # 除缓存读写外的额外 MCP 工具
    max_turns: int = 8,
    timeout_seconds: int = 60,
) -> SubagentConfig
```

### 参数详解

| 参数 | 说明 | 示例 |
|------|------|------|
| `agent_name` | 全局唯一，建议 `sc2-<功能>` | `"sc2-counter"` |
| `description` | 中文一句话，说明输入输出 | `"兵种克制分析：…"` |
| `role` | 注入 prompt 的职责描述 | `"识别敌方主力，给出克制建议"` |
| `input_sources` | 上游 **缓存键**（非 `sc2-` 前缀名） | `["sensing", "compute"]` |
| `output_json_schema` | 期望 JSON 字段与类型示意 | 见下文案例 |
| `extra_tools` | 可选 MCP 工具名列表 | `["sc2_unit_capabilities"]` |
| `max_turns` / `timeout_seconds` | 推理轮次与超时 | 默认 8 / 60 |

### 默认工具集

模板会自动挂载：

- `sc2_analysis_cache_get`
- `sc2_analysis_cache_set`
- 以及你在 `extra_tools` 中声明的工具

## 4. 接入步骤（四步）

### 步骤 1：新建智能体文件

在项目中创建独立模块，例如 `sc2_counter.py`：

```python
from create_new_agent import create_new_agent
from sc2_agents import ALL_SC2_SUBAGENTS

counter_agent = create_new_agent(
    agent_name="sc2-counter",
    description="兵种克制分析：基于 sensing 和 compute 数据，推荐最优克制单位",
    role="识别敌方主力单位类型，给出克制生产建议",
    input_sources=["sensing", "compute"],
    output_json_schema={
        "enemy_main_composition": {"unit_type": "string", "count": "int"},
        "counters": [
            {"our_unit": "string", "effectiveness": "float", "action": "produce|tech"}
        ],
        "urgent_switch": "boolean",
    },
    extra_tools=["sc2_unit_capabilities"],
    max_turns=6,
    timeout_seconds=45,
)

ALL_SC2_SUBAGENTS["sc2-counter"] = counter_agent
```

### 步骤 2：设计 output_json_schema

- 用 **Python dict** 描述字段名与类型示意（`string` / `int` / `float` / `boolean` 或嵌套结构）。
- 字段应**可机器消费**：下游智能体或编排层会直接解析，避免自由文本占主导。
- 复杂枚举可在值里用 `"produce|tech"` 等形式提示模型。

### 步骤 3：声明 input_sources

- 只列出**本智能体实际会读**的上游阶段。
- 使用缓存键：`sensing`、`compute`、`disposition`、`intent`、`risk_id`、`risk_response`（与 `sc2_agents.py` 中各阶段 `agent_name=` 一致）。
- 若需空间信息，在 `extra_tools` 中加 `sc2_get_layer`；若需静态单位属性，加 `sc2_unit_capabilities`。
- **不确定读什么？** 见 [SC2数据与智能体输入说明.md §7 决策树](./SC2数据与智能体输入说明.md#7-设计新智能体输入选型决策树) 与 [§5 各阶段 schema](./SC2数据与智能体输入说明.md#5-layer-2流水线缓存各阶段输入输出)。

### 步骤 4：注册到总字典

所有 SC2 子智能体统一注册到 `ALL_SC2_SUBAGENTS`：

```python
ALL_SC2_SUBAGENTS["sc2-<你的智能体名>"] = your_agent
```

编排层通过该字典发现并调度子智能体。新增键名必须与 `agent_name` 完全一致。

### 4.1 并入主流水线（`SC2_SUBAGENT_ORDER`）

仅写入 `ALL_SC2_SUBAGENTS` **不够**。主流水线 `run_sc2_deerflow_pipeline.py`（本目录有副本）按列表**顺序**执行；未出现在列表中的注册名**永远不会被调用**。

在 **SwarmBrain 项目根目录** 的 `run_sc2_deerflow_pipeline.py` 中修改 `SC2_SUBAGENT_ORDER`，例如将 `sc2-counter` 插在 compute 与 disposition 之间：

```python
SC2_SUBAGENT_ORDER = [
    "sc2-sensing",
    "sc2-compute",
    "sc2-counter",      # 新增：须在 ALL_SC2_SUBAGENTS 中已注册
    "sc2-disposition",
    "sc2-intent",
    "sc2-risk-id",
    "sc2-risk-response",
]
```

| 注意点 | 说明 |
|--------|------|
| 顺序即依赖 | 排在你后面的阶段才能通过 `cache_get` 读到你的输出；`input_sources` 只能引用**排在你前面**的缓存键 |
| 缓存键 | 由 `_stage_agent_key()` 推导：`sc2-counter` → `counter`；与 `create_new_agent` 模板一致 |
| 合并后同步 | 改根目录脚本后，建议把 `new_agents/run_sc2_deerflow_pipeline.py` 副本一并更新，避免同学文档与代码不一致 |
| 联调 | `python run_sc2_deerflow_pipeline.py --thread-id <与集成同学约定>`，检查 `sc2:analysis:<thread_id>:counter` |

**运行环境**：流水线依赖 `sc2_redis_tools.py`、`swarmbrain_llm_shared.py`、Redis、`situation:current`，请在完整仓库根目录执行，不要仅在 `new_agents` 子目录运行副本。

**仪表盘**：合并后，Ask API「刷新分析」会子进程调用根目录同一脚本；前端要能展示你的阶段，还需集成同学改 `ask_api_server.py` / 仪表盘（若尚未消费新 cache 键）。

## 5. 参考案例：sc2-counter（兵种克制）

`sc2_counter.py` 演示了一个典型的**中游分析型**智能体：

| 维度 | 设计 |
|------|------|
| 定位 | 在 sensing（原始单位统计）与 compute（战力聚合）之上做克制推理 |
| 上游 | `sensing`、`compute` |
| 额外工具 | `sc2_unit_capabilities` — 查询单位属性以计算克制关系 |
| 输出 | 敌方主力构成、克制列表、是否需紧急转型 |
| 资源 | `max_turns=6`，`timeout_seconds=45`（比默认更紧，适合轻量推理） |

### 建议插入流水线位置

```
… → sc2-compute → sc2-counter → sc2-disposition → …
```

具体顺序必须在根目录 `run_sc2_deerflow_pipeline.py` 的 `SC2_SUBAGENT_ORDER` 中显式插入（见 §4.1），不存在「自动并行分支」。

## 6. 主流水线行为摘要（阅读 `run_sc2_deerflow_pipeline.py`）

下发包内的 `run_sc2_deerflow_pipeline.py` 与仓库根目录同源，建议结合 [SC2数据与智能体输入说明.md §2.1](./SC2数据与智能体输入说明.md#21-主流水线编排run_sc2_deerflow_pipelinepy) 阅读。

| 机制 | 对你接入的影响 |
|------|----------------|
| `run_stage()` | 每个阶段：SystemMessage = 你的 `system_prompt`；HumanMessage 含 `thread_id` + `mode` |
| `cfg.tools` | 仅列表中的工具可被 LLM 调用；与 `create_new_agent(..., extra_tools=[...])` 一致 |
| `max_turns` / `timeout_seconds` | 来自你的 `SubagentConfig`；超时则跳过 backfill，该阶段 cache 可能为空 |
| JSON backfill | 模型若忘记 `sc2_analysis_cache_set`，编排器尝试从最后一轮文本抠 JSON 写入 Redis |
| `--replay` | `mode=replay` 且 risk-response 无 `sc2_send_commands` |

## 7. 可选 MCP 工具速查

| 工具 | 用途 |
|------|------|
| `sc2_get_situation` | 全量局势快照（通常仅 sensing 阶段使用） |
| `sc2_get_layer` | 分层数据：`unit` / `economy` / `map` / `vision` |
| `sc2_unit_capabilities` | 单位静态属性（DPS、射程、成本等） |
| `sc2_get_trend` | 近 30s 趋势变化 |
| `sc2_get_game_status` | 游戏运行状态 |
| `sc2_send_commands` | 下发操作指令（慎用，多见于 risk-response） |
| `sc2_analysis_cache_get` | 读 staged JSON（模板已内置） |
| `sc2_analysis_cache_set` | 写 staged JSON（模板已内置） |

**原则**：能通过上游缓存拿到的数据，不要重复调用 `sc2_get_situation` 或全量 layer 拉取。

## 8. 与 sc2_agents.py 手写配置的对应关系

以 `SC2_COMPUTE` 为例，手写配置包含：

- `name` / `description` → 对应 `agent_name` / `description`
- `system_prompt` 中的职责与流程 → 由 `role`、`input_sources`、`output_json_schema` 自动生成
- `tools` → 默认缓存工具 + `extra_tools`
- `disallowed_tools` / `model` → 模板内固定为 `["task", "ask_clarification"]` / `"inherit"`

若需像 `SC2_INTENT` 那样在 prompt 中加入**硬性业务条款**（例如「四个维度必须齐全」），有两种做法：

1. **扩展模板**：在 `create_new_agent.py` 增加可选参数 `extra_prompt_rules: str`。
2. **局部手写**：该智能体仍用 `SubagentConfig` 手写，不经过模板。

## 9. 接入检查清单

接入新智能体前，请逐项确认：

- [ ] `agent_name` 全局唯一，且符合 `sc2-<短名>` 规范
- [ ] `input_sources` 中的键与已有阶段的缓存 `agent_name` 一致
- [ ] `output_json_schema` 字段完整、类型清晰，且与下游消费方对齐
- [ ] 已声明必要的 `extra_tools`，且未重复请求上游已有数据
- [ ] 已写入 `ALL_SC2_SUBAGENTS[agent_name]`
- [ ] 根目录 `run_sc2_deerflow_pipeline.py` 的 `SC2_SUBAGENT_ORDER` 已加入本阶段且顺序正确（§4.1）
- [ ] 本地或联调环境中验证：`cache_get` → 推理 → `cache_set` → 下游能读到 JSON

## 10. 常见问题

### Q1：`agent_name` 写 `counter` 还是 `sc2-counter`？

注册与字典键用 **`sc2-counter`**；写入 Redis 时模板会自动使用 **`counter`** 作为 `agent_name` 参数。

### Q2：`input_sources` 里要写 `sc2-sensing` 吗？

不要。写缓存键 **`sensing`**，与 `sc2_analysis_cache_set(..., agent_name="sensing")` 保持一致。

### Q3：能否跳过 cache，直接输出 JSON？

不可以。流水线依赖 Redis 缓存传递结构化产物；跳过会导致下游无法读取。

### Q4：需要人工确认再执行命令怎么办？

参考 `SC2_RISK_RESPONSE`：在 JSON 中设计 `mode`、`hitl_required` 等字段，并仅在确认后调用 `sc2_send_commands`。此类逻辑较复杂，建议手写 `SubagentConfig` 或扩展模板。

### Q5：只改了 `sc2_agents.py`，流水线仍不跑我的智能体？

检查**两处**：① `ALL_SC2_SUBAGENTS["sc2-xxx"]` 已注册；② 根目录 `SC2_SUBAGENT_ORDER` 包含 `"sc2-xxx"`。缺②则编排器不会调度。

### Q6：`new_agents` 目录里能直接 `python run_sc2_deerflow_pipeline.py` 吗？

**不能**。副本用于阅读；运行需要项目根的 `sc2_redis_tools.py`、`swarmbrain_llm_shared.py`、Redis 与 LLM 配置。

## 12. 最小可复制模板

复制以下内容，替换尖括号占位符即可开始：

```python
from create_new_agent import create_new_agent
from sc2_agents import ALL_SC2_SUBAGENTS

<模块名>_agent = create_new_agent(
    agent_name="sc2-<短名>",
    description="<调度层可见的中文描述>",
    role="<一句话职责>",
    input_sources=["<上游缓存键1>", "<上游缓存键2>"],
    output_json_schema={
        "<字段名>": "<类型或嵌套结构>",
    },
    extra_tools=[],  # 如 ["sc2_get_layer"]
    max_turns=8,
    timeout_seconds=60,
)

ALL_SC2_SUBAGENTS["sc2-<短名>"] = <模块名>_agent
```

完成注册后，在编排层配置中增加对该子智能体的调用，即可接入主工作流。
